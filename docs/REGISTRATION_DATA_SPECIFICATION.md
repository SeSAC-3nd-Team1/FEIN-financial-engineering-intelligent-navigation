# 회원가입 데이터 명세서

> 상태: 목표 설계안(Target Design)
> 기준 이슈: #24
> 대상 DB: PostgreSQL
> 정규화 목표: 제3정규형(3NF)

## 1. 목적

프론트엔드 회원가입 명세 Version 1.0의 가입 흐름을 PostgreSQL과 Redis에 역할별로 분리하고, 회원/약관/동의 데이터를 제3정규형으로 저장하기 위한 기준 문서다.

이 문서는 현재 운영 중인 ORM 스키마를 설명하는 문서가 아니라 **다음 migration에서 구현할 목표 스키마**를 정의한다.

## 2. 원본 명세에서 유지하는 요구사항

- 가입 완료 계정은 최종 `POST /users/signup`에서만 생성한다.
- 휴대폰과 이메일은 가입 전 각각 검증되어야 한다.
- OTP는 6자리이며 서버가 만료와 시도 횟수를 권위 있게 관리한다.
- OTP TTL은 300초다.
- verification token은 30분 TTL과 single-use 정책을 가진다.
- 약관 동의는 약관 code와 version 단위로 감사 가능해야 한다.
- 비밀번호 평문은 DB나 로그에 저장하지 않는다.
- CI/DI는 평문 저장하지 않는다.
- 최종 회원 생성과 회원 약관 동의 저장은 하나의 PostgreSQL transaction으로 처리한다.

## 3. 이번 3NF 설계에서 변경하는 부분

### 3.1 인증 boolean 제거

기존의 `phone_verified`, `email_verified`는 각각 `phone_verified_at`, `email_verified_at`에서 파생할 수 있으므로 목표 스키마에서 제거한다.

- `phone_verified_at IS NOT NULL` -> 휴대폰 인증 완료
- `email_verified_at IS NOT NULL` -> 이메일 인증 완료

동일한 사실을 boolean과 timestamp 두 컬럼에 중복 저장하지 않는다.

### 3.2 약관 참조를 `term_id`로 단일화

`user_agreements`에 `term_code`, `term_version`, `is_required`를 반복 저장하지 않는다.

약관 자체의 속성은 `terms`에만 저장하고 동의 테이블은 특정 약관 version row의 PK인 `term_id`만 참조한다.

### 3.3 가입 전 상태를 별도 관계로 분리

가입 완료 전 개인정보와 약관 동의는 `users`에 넣지 않는다.

- `registration_sessions`: 가입 진행 중 개인정보/검증 완료 시각
- `registration_agreements`: 가입 진행 중 약관 선택 상태

가입 성공 시 이 데이터를 사용해 `users`, `user_agreements`를 생성하고 임시 가입 상태는 완료/정리한다.

### 3.4 OTP와 verification token은 Redis에 저장

OTP hash, attempts, TTL, verificationId, verification token single-use 상태와 rate limit은 PostgreSQL 영구 데이터가 아니므로 Redis가 담당한다.

## 4. 저장소 책임 경계

| 저장소 | 데이터 | 보존 성격 |
| --- | --- | --- |
| PostgreSQL `users` | 가입 완료 회원 | 영구 |
| PostgreSQL `terms` | 약관 catalog/version | 영구/불변 이력 |
| PostgreSQL `user_agreements` | 회원 약관 동의 이력 | 영구/감사 |
| PostgreSQL `registration_sessions` | 가입 진행 중 개인정보 | 임시 |
| PostgreSQL `registration_agreements` | 가입 진행 중 약관 선택 | 임시 |
| Redis | OTP hash, attempts, TTL, verificationId, verification token 상태, rate limit | 단기 TTL |

## 5. 3NF 근거

### 5.1 함수적 종속성

목표 관계의 주요 함수적 종속성은 다음과 같다.

```text
users.id -> users의 모든 비키 속성

terms.id -> term_code, version, title, content_reference,
            is_required, effective_at, created_at
(term_code, version) -> terms.id 및 약관 version의 모든 속성

user_agreements.id -> user_id, term_id, is_agreed,
                      agreed_at, agreed_ip, user_agent
(user_id, term_id) -> 동의 사실과 감사 속성

registration_sessions.id -> 가입 진행 상태의 모든 속성

registration_agreements.(registration_id, term_id)
    -> is_agreed, agreed_at, agreed_ip, user_agent
```

### 5.2 제거하는 부분 종속/이행 종속

기존 형태에서 다음 값은 동의 행 자체가 아니라 약관 version에 종속된다.

```text
(term_code, term_version) -> is_required
```

따라서 `user_agreements.is_required`를 제거한다.

또한 다음처럼 동일 사실을 두 컬럼으로 표현하지 않는다.

```text
phone_verified_at -> phone verification 상태
email_verified_at -> email verification 상태
```

따라서 `phone_verified`, `email_verified`를 제거한다.

## 6. PostgreSQL 테이블 명세

# 6.1 users

가입이 완료된 계정만 저장한다.

| 컬럼 | PostgreSQL 타입 | NULL | 제약/기본값 | 설명 |
| --- | --- | --- | --- | --- |
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | N | PK | 내부 회원 식별자 |
| `user_id` | `VARCHAR(16)` | N | UNIQUE | 로그인 ID. 저장 전 lowercase 정규화 |
| `password_hash` | `VARCHAR(255)` | N |  | Argon2id 또는 bcrypt hash |
| `name` | `VARCHAR(30)` | N |  | 본인확인 기준 이름 |
| `birthdate` | `CHAR(6)` | N | CHECK digits | YYMMDD 원형 보존 |
| `phone_number` | `VARCHAR(11)` | N | INDEX | 숫자만 저장, unique 아님 |
| `phone_verified_at` | `TIMESTAMPTZ` | N |  | 가입에 사용한 휴대폰 인증 완료 시각 |
| `email` | `VARCHAR(255)` | N | UNIQUE | trim/lowercase 정규화 |
| `email_verified_at` | `TIMESTAMPTZ` | N |  | 이메일 인증 완료 시각 |
| `ci_encrypted` | `BYTEA` | Y |  | CI 암호화 ciphertext |
| `ci_lookup_hash` | `BYTEA` | Y | UNIQUE | CI 중복 탐색용 keyed HMAC |
| `di_encrypted` | `BYTEA` | Y |  | DI 암호화 ciphertext |
| `telecom_carrier` | `VARCHAR(20)` | Y |  | 본인확인 사업자 반환값 |
| `gender` | `VARCHAR(1)` | Y |  | 본인확인 사업자 반환값 |
| `member_type` | `VARCHAR(20)` | N | DEFAULT `ASSOCIATE` | `ASSOCIATE`, `FULL` |
| `account_status` | `VARCHAR(20)` | N | DEFAULT `ACTIVE` | `ACTIVE`, `DORMANT`, `SUSPENDED`, `WITHDRAWN` |
| `last_login_at` | `TIMESTAMPTZ` | Y |  | 최근 로그인 시각 |
| `active_operation_mode` | `VARCHAR(20)` | Y | CHECK | 현재 선택한 `AUTO`/`SEMI_AUTO` 가상계좌 방식 |
| `operation_mode_changed_at` | `TIMESTAMPTZ` | Y |  | 최초 활성화 또는 마지막 명시적 전환 시각 |
| `created_at` | `TIMESTAMPTZ` | N | `now()` | 생성 시각 |
| `updated_at` | `TIMESTAMPTZ` | N | `now()` | 수정 시각 |
| `deleted_at` | `TIMESTAMPTZ` | Y |  | soft delete 시각 |

### 주요 CHECK

```text
user_id ~ '^[a-z0-9]{6,16}$'
email = lower(email)
birthdate ~ '^[0-9]{6}$'
phone_number ~ '^0[0-9]{9,10}$'
member_type IN ('ASSOCIATE', 'FULL')
account_status IN ('ACTIVE', 'DORMANT', 'SUSPENDED', 'WITHDRAWN')
active_operation_mode IN ('AUTO', 'SEMI_AUTO')
account_status = 'WITHDRAWN' -> deleted_at IS NOT NULL
```

### 주요 index

- `uq_users_user_id` UNIQUE (`user_id`)
- `uq_users_email` UNIQUE (`email`)
- `uq_users_ci_lookup_hash` UNIQUE (`ci_lookup_hash`)
- `ix_users_phone_number` (`phone_number`)

# 6.2 terms

약관을 `term_code + version` 단위의 불변 catalog로 저장한다.

| 컬럼 | PostgreSQL 타입 | NULL | 제약/기본값 | 설명 |
| --- | --- | --- | --- | --- |
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | N | PK | 약관 version 식별자 |
| `term_code` | `VARCHAR(30)` | N |  | 약관 논리 코드 |
| `version` | `VARCHAR(20)` | N |  | 약관 버전 |
| `title` | `VARCHAR(200)` | N |  | 약관명 |
| `content_reference` | `VARCHAR(500)` | Y |  | immutable 전문 URL/문서 참조 |
| `is_required` | `BOOLEAN` | N |  | 해당 version 필수 여부 |
| `effective_at` | `TIMESTAMPTZ` | N |  | 효력 발생 시각 |
| `created_at` | `TIMESTAMPTZ` | N | `now()` | catalog 등록 시각 |

### 제약

- UNIQUE (`term_code`, `version`)
- 기존 version row를 수정하지 않고 새 version row를 추가한다.
- `user_agreements` 또는 `registration_agreements`가 참조한 약관은 삭제하지 않는다.

### 현재 유효 catalog와 seed

- API에서 현재 유효한 약관은 `effective_at <= now()`인 row 중 `term_code`별 최신 version이다.
- 별도 `is_active` 컬럼은 두지 않는다. 미래 효력 version과 최신 version으로 대체된 과거 row는 신규 가입에 사용할 수 없다.
- 현재 유효한 필수 약관이 한 건도 없으면 회원가입은 `TERMS_CATALOG_UNAVAILABLE`로 중단한다.
- 로컬 Docker는 migration 후 기존 6종 약관을 `dev-` version으로 멱등 seed한다. 운영은 승인된 version과 효력 시각, 불변 `content_reference`를 별도로 지정한다.

# 6.3 user_agreements

가입 완료 회원의 약관 version별 동의 사실을 저장한다.

| 컬럼 | PostgreSQL 타입 | NULL | 제약/기본값 | 설명 |
| --- | --- | --- | --- | --- |
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | N | PK | 감사 행 식별자 |
| `user_id` | `BIGINT` | N | FK -> `users.id` | 회원 |
| `term_id` | `BIGINT` | N | FK -> `terms.id` | 특정 약관 version |
| `is_agreed` | `BOOLEAN` | N |  | 동의 여부 |
| `agreed_at` | `TIMESTAMPTZ` | Y |  | 동의한 경우 시각 |
| `agreed_ip` | `INET` | Y |  | 동의 요청 IP |
| `user_agent` | `VARCHAR(512)` | Y |  | 동의 클라이언트 User-Agent |

### 제약

- UNIQUE (`user_id`, `term_id`)
- `is_agreed = true`이면 `agreed_at IS NOT NULL`
- `terms` FK는 `ON DELETE RESTRICT`
- `users`는 soft delete가 기본이므로 FK는 `ON DELETE RESTRICT`

`is_required`, `term_code`, `term_version`은 저장하지 않는다. 필요 시 `terms` JOIN으로 조회한다.

# 6.4 registration_sessions

가입 완료 전 개인정보와 인증 완료 상태를 임시 저장한다.

| 컬럼 | PostgreSQL 타입 | NULL | 제약/기본값 | 설명 |
| --- | --- | --- | --- | --- |
| `id` | `UUID` | N | PK | 가입 세션 식별자 |
| `name` | `VARCHAR(30)` | N |  | Step 01 이름 |
| `birthdate` | `CHAR(6)` | N | CHECK digits | Step 01 생년월일 |
| `phone_number` | `VARCHAR(11)` | N | INDEX | Step 01 휴대폰 번호 |
| `phone_verified_at` | `TIMESTAMPTZ` | Y |  | 휴대폰 OTP 검증 완료 시각 |
| `email` | `VARCHAR(255)` | Y |  | Step 03 이메일 |
| `email_verified_at` | `TIMESTAMPTZ` | Y |  | 이메일 OTP 검증 완료 시각 |
| `created_at` | `TIMESTAMPTZ` | N | `now()` | 세션 생성 시각 |
| `expires_at` | `TIMESTAMPTZ` | N |  | 가입 세션 만료 시각 |
| `completed_at` | `TIMESTAMPTZ` | Y |  | 회원 생성 완료 시각 |

### 정책

- 비밀번호와 OTP code는 절대 저장하지 않는다.
- `completed_at IS NULL AND expires_at < now()`인 세션은 정리 대상이다.
- MVP 세션 TTL은 verification token TTL에 맞춰 30분을 기본값으로 사용하되 운영 정책 확정 시 변경 가능하다.
- 가입 완료 후 즉시 또는 짧은 보존 유예 후 개인정보를 삭제한다.

# 6.5 registration_agreements

가입 완료 전에 사용자가 선택한 약관 version별 상태를 저장한다.

| 컬럼 | PostgreSQL 타입 | NULL | 제약/기본값 | 설명 |
| --- | --- | --- | --- | --- |
| `registration_id` | `UUID` | N | PK/FK -> `registration_sessions.id` | 가입 세션 |
| `term_id` | `BIGINT` | N | PK/FK -> `terms.id` | 특정 약관 version |
| `is_agreed` | `BOOLEAN` | N |  | 선택 상태 |
| `agreed_at` | `TIMESTAMPTZ` | Y |  | 동의한 경우 시각 |
| `agreed_ip` | `INET` | Y |  | 요청 IP |
| `user_agent` | `VARCHAR(512)` | Y |  | 클라이언트 User-Agent |

### 제약

- PRIMARY KEY (`registration_id`, `term_id`)
- `registration_sessions` FK `ON DELETE CASCADE`
- `terms` FK `ON DELETE RESTRICT`
- `is_agreed = true`이면 `agreed_at IS NOT NULL`

## 7. 관계 cardinality

```text
users 1 ---- N user_agreements N ---- 1 terms

registration_sessions 1 ---- N registration_agreements N ---- 1 terms
```

가입 전과 가입 후 동의 데이터는 서로 다른 관계로 분리한다.

## 8. Redis 명세

Redis는 관계형 원장이 아니라 단기 검증 상태를 담당한다.

### 8.1 OTP challenge

권장 key 예시:

```text
signup:verification:{verification_id}
```

값의 논리 필드:

```text
channel          PHONE | EMAIL
target           전화번호 또는 이메일
registration_id  UUID
code_hash        OTP hash
attempts         현재 실패 횟수
max_attempts     5
purpose          SIGNUP
issued_at
```

- Redis key TTL: 300초
- raw OTP는 저장하지 않는다.
- 새 OTP 발급 시 동일 target/purpose의 이전 challenge는 무효화한다.

### 8.2 verification token state

JWT 자체에 필요한 claim을 포함하더라도 single-use 보장을 위해 server-side consume state를 둔다.

권장 key 예시:

```text
signup:token:{jti}
```

논리 필드:

```text
channel
registration_id
target
consumed
```

- TTL: 30분
- signup 성공 transaction과 token consume 사이의 실패 복구를 위해 예약 -> DB commit -> 확정 상태 전이를 사용한다.

### 8.3 rate limit

```text
signup:rate:phone:{phone_number}
signup:rate:email:{email}
signup:rate:ip:{ip}
```

API 명세의 target/IP rate limit을 Redis counter + TTL로 구현한다.

## 9. 가입 데이터 흐름

```text
1. Step 01
   registration_sessions 생성
   registration_agreements 저장
   Redis phone OTP challenge 생성

2. Phone verify
   Redis OTP 검증/소비
   registration_sessions.phone_verified_at 갱신
   phone verification token 발급

3. Email send/verify
   registration_sessions.email 저장
   Redis email OTP challenge 생성/검증
   registration_sessions.email_verified_at 갱신
   email verification token 발급

4. Signup
   두 verification token과 registration_id 검증
   user_id/password/email 최종 validation

   PostgreSQL transaction BEGIN
     users INSERT
     registration_agreements -> user_agreements INSERT SELECT
     registration_sessions.completed_at 갱신
   COMMIT

5. transaction 성공 후
   verification token consume 확정
   registration 임시 개인정보 정리 예약
```

## 10. 현재 구현 상태

Alembic `20260816_0011`에서 회원가입 관계의 3NF 전환이 완료되었다. `users`는 인증 timestamp만 사용하고, `user_agreements`는 `term_id` FK만 보유하며, 회원/약관 감사 FK는 `RESTRICT`다. Backend 회원가입은 현재 유효 catalog의 필수 동의를 검증하고 같은 transaction에서 `users`와 `user_agreements`를 생성한다. `20260825_0021`은 금융 계좌 데이터를 옮기지 않고 사용자의 현재 화면 선택만 복원하기 위해 nullable `active_operation_mode`와 변경 시각을 추가한다.

`registration_sessions`와 `registration_agreements` schema는 준비되어 있지만 실제 OTP provider 및 가입 세션 API 연결은 후속 범위다. 현재 Backend request의 `phone_verified`/`email_verified`는 MVP API 계약이며 실제 외부 인증 완료 증명으로 교체해야 한다.

## 11. 후속 구현 범위

설계 승인 후 별도 구현 단계에서 수행한다.

1. Redis signup verification repository 구현
2. 실제 휴대폰/이메일 OTP provider 연결
3. `registration_sessions` 기반 단계별 가입 API 연결
4. 가입 transaction과 verification token consume 상태 전이 구현
5. Azure PostgreSQL 운영 약관 version 적용

## 12. 구현 전 확인할 정책

- 가입 세션 TTL과 완료 후 임시 개인정보 삭제 시점
- 실제 운영 약관 version 및 immutable 전문 저장 위치
- 탈퇴 후 ID/email/CI 재사용 여부
- CI/DI Key Vault envelope/key rotation 형식
- 가입 transaction과 Redis token consume 사이의 장애 복구 방식
- 선택 약관이 추가될 경우 `is_agreed=false`도 영구 감사 대상으로 보존할지 여부
